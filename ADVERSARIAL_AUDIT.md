## 1. Executive assessment

The runtime is small (≈2.5k lines of production code) and most of the lifecycle, resource-ownership and configuration paths hold up under inspection; a number of plausible defects were ruled out with primary-source evidence (§2.3). The release risks that remain are concentrated in the two recently added mechanisms and in one renderer interaction:

1. **The new lost-rebuild retry does not cover the window Sodium actually drops requests in.** Sodium ignores `scheduleRebuild` only while a section has never been built (`!section.isBuilt()`), i.e. while its *initial build is in flight*. The mod's acknowledgment is written per block by the meshing worker with last-write-wins, so an initial build that straddles a snapshot/progress/appearance change produces a torn mesh *and* records the newest state as "current". The retry then never fires. `LostRebuildTest` exercises a different scenario (requests dropped while no mesh is in flight), which the retry does handle. (F2)
2. **Unchanged recaptures replace the snapshot object, and identity-based freshness then schedules a retry rebuild anyway.** This silently undoes the "identical environment ⇒ no remesh" guarantee for every *queued* recapture; the ground system recaptures eight neighbours on every chunk load, so exploring a snowy forest produces a steady stream of unnecessary section rebuilds. (F3)
3. **Sodium + "Fast" graphics draws the snow overlay as an opaque, hole-less blanket — reproduced in this audit.** Sodium forces every quad a leaf block emits into its solid pass (`BlockRenderer.processQuad`: `forceOpaque ? SOLID : blendMode`), that pass is compiled without `ALPHA_CUTOUT`, and Minecraft 26.3's `TextureUtil.solidify` has already painted every transparent mask texel with the nearest snow colour at atlas load. So wherever the overlay has a hole — the depth taper dither, and every not-yet-whitened texel during buildup — Sodium Fast shows solid snow instead of the leaf underneath. The `depth-50-fast` capture from the Prism instance (Sodium 0.9.2, shaders off) shows the dithered 50 %-depth band of the Fancy capture replaced by a solid two-tone grey band with a hard lower edge. The standard (Indigo) renderer honours the overlay's `CUTOUT` layer and is unaffected. Not black speckles, as the initial static read predicted — the runtime check corrected that. (F1)
4. Falling-leaf particle sprites are copied at full source resolution with no size cap or budget. (F4)

**Limits of the evidence.** This environment has no display, so Gradle-launched client fixtures could not run. One client fixture was executed through the user's Prism `Release-Test` instance (the depth scenario, Sodium 0.9.2 with Iris loaded but shaders disabled) to settle F1; every other rendering, Sodium and Iris claim is static analysis against the exact pinned sources, and no shader pack was exercised. The JUnit suite (92 tests) was run fresh and passes, but it covers only the pure `core`/`config` packages; `SnowSystem`, `GroundSnowSystem`, `SnowModels` and the mixins have no automated coverage outside the manual client tests. Multiplayer/dedicated-server behaviour was not exercised (the docs say the same).

## 2. Prioritized findings

Severity: **Critical / Major / Moderate / Minor**. Confidence (separate): **Confirmed** (reproduced), **High** (decisive static proof against primary sources), **Medium** (static, with a stated assumption), **Low**.

### F1 — Sodium + Fast graphics: snow overlay drawn in the solid pass, so its transparent texels render as opaque snow (no taper, no gradual buildup)
- **Severity:** Moderate (visual regression for Sodium users with Fancy Leaves off: the 50 % default depth loses its dithered edge, and buildup degenerates to per-face all-or-nothing; nothing crashes and Fancy mode is correct). **Confidence:** Confirmed for the taper band; High (same verified mechanism, not captured) for the buildup phase. **Status:** **Reproduced** in the Prism instance on 2026-10-26 (see §6).
- **Location:** `src/client/java/dev/frostedfoliage/client/render/SnowModels.java:252-262` (`frost()` sets `chunkLayer(ChunkSectionLayer.CUTOUT)` on the overlay); `SnowMath.snowPixel`/`depthPixel`/`PlantSnow.pixel` return `0` (ARGB 0 = transparent *black*) for masked-out texels (`core/SnowMath.java:74,78,108,114`, `core/PlantSnow.java:15,20,23`).
- **Reachable path:** Sodium 0.9.2 `BlockRenderer.renderModel` sets `this.forceOpaque = ModelBlockRenderer.forceOpaque(cutoutLeaves, state)` for leaves when the Graphics option is Fast, then `processQuad` chooses `DefaultMaterials.forChunkLayer(this.forceOpaque ? ChunkSectionLayer.SOLID : blendMode)` for **every** quad emitted during `emitModel`, including the mod's overlay. `DefaultTerrainRenderPasses.SOLID = new TerrainRenderPass(SOLID, false, /*allowFragmentDiscard*/ false)`; `block_layer_opaque.fsh` discards only `#ifdef ALPHA_CUTOUT`. The overlay is offset 0.002 outward from the base face, so it is drawn on top.
- **What actually renders (verified):** the masks store holes as ARGB 0, but `MipmapGenerator.generateMipLevels` (26.3) applies `TextureUtil.solidify` to mip level 0 of every non-`item/` sprite that has transparent pixels (AUTO strategy → `CUTOUT`): a BFS from opaque texels gives each alpha-0 texel the RGB of its nearest opaque neighbour while keeping alpha 0. In the cutout pass those texels are still discarded; in Sodium's solid pass (no discard) they are drawn with that borrowed snow colour. So under Sodium + Fast the overlay is an opaque blanket: (a) at intermediate `snowDepth` (default 0.5) the dithered taper band (`depthPixel` zeros) becomes solid snow down to the hard geometric clip — **reproduced** (`depth-50-fast` vs `depth-50`, pixel-aligned: inside the band rows of the nearest tree face, "green" pixels fall from 444 to 36, and the 4× crops show a two-tone grey block with a straight lower edge instead of dither with green showing through); (b) during buildup every texel the patch noise has not yet whitened (`snowPixel` returns 0 when `patch >= stage/16`) is likewise filled, so a face with any overlay at all reads as fully snowed — same mechanism, not captured because no fixture takes a Fast capture during accumulation; (c) the leaf texture's own holes are filled by the same `solidify` call in vanilla, which is why vanilla Fast leaves are not black (their PNGs store (0,0,0) under alpha 0) and why the overlay shows no black either. At `snowDepth = 1` and full coverage the overlay's holes coincide with the base's and nothing differs (`canopy-06-fast`).
- **Why the standard renderer is unaffected:** the Fabric default `FabricBlockStateModel.emitQuads` applies `forceOpaque` as a `pushTransform` on the emitter it is given — the mod's interceptor `worker.input` — so the *base* quads arrive as SOLID, but the overlay is emitted on `output` after `frost()` sets CUTOUT, and Indigo honours per-quad layers (vanilla's `SectionCompiler` likewise routes only the block's own quads through `opaqueQuadOutput`).
- **Evidence:** Sodium `common/src/main/java/net/caffeinemc/mods/sodium/client/render/chunk/compile/pipeline/BlockRenderer.java` (`renderModel`, `processQuad`), `DefaultTerrainRenderPasses.java`, `assets/sodium/shaders/blocks/block_layer_opaque.fsh` — tag `mc26.3-0.9.2` and the pinned jar; Minecraft 26.3 `MipmapGenerator.generateMipLevels` and `com.mojang.blaze3d.platform.TextureUtil.solidify`; the Prism run in §6 (captures `0010_depth-50.png`, `0013_depth-50-fast.png`, crops `left-fancy-4x.png`/`left-fast-4x.png` in the audit scratchpad). The docs' earlier Fast-leaves checks (`docs/images/bsl-fast.png`, `snow-depth-50.png`, local untracked files) were taken with BSL or Complementary active, whose terrain shaders alpha-test the solid pass and so hid the defect; the audit's own before/after captures are `docs/images/sodium-fast-depth-50-before.png` and `-after.png` beside `depth-50-fancy-sodium.png` (same folder, likewise untracked).
- **Which capture shows it:** the main fixture's `06-fast-leaves` is taken at `snowDepth(1)` and full coverage (`FrostedFoliageGameTest.java:65-66,123-127`) — precisely the configuration where the defect is invisible. The depth fixture's `depth-50-fast` (`CanopyAppearanceTest.java:123-132`: 50 % depth, Fast leaves, full snow) shows it, **with shaders off**: under Iris with a pack active the pack's own terrain shaders replace Sodium's `block_layer_opaque.fsh`, so a shader run neither confirms nor clears it (the Prism instance launches with `shaderExpected=true` cached; the audit overrode it with `shaderExpected=false` in `frostedfoliage-test.properties` and `enableShaders=false`). No fixture takes a Fast capture during accumulation, so case (b) remains visually unconfirmed.
- **Smallest fix:** `ModelBlockRenderer.forceOpaque(boolean, BlockState)` is public static; in `SnowModel.emitQuads` compute `forced = ModelBlockRenderer.forceOpaque(Minecraft.getInstance().options.cutoutLeaves().get(), state)` and, when `forced && FabricLoader.getInstance().isModLoaded("sodium")`, emit the wrapped model without the leaf overlay (plants are not `LeavesBlock`, and ground-snow quads are explicitly SOLID with an opaque texture, so only leaf overlays need the guard). Users keep Fancy-mode snow; Fast mode under Sodium shows plain leaves instead of a hole-less blanket. A fuller fix (opaque composite masks for Fast mode) doubles atlas cost and cannot reproduce the biome tint per texel, so it is not recommended as the first step.
- **Regression test:** emission-level and deterministic: with `cutoutLeaves=false` under `-PtestRenderer=sodium`, emit the snowy leaf model through the renderer and assert that no quad whose sprite is `frostedfoliage:generated/...` is emitted for a `LeavesBlock` (or, after a non-suppression fix, that none lands in the solid pass); plus a pixel check on `depth-50-fast` versus `depth-50` of the same scene — the share of green pixels inside the snow band of the nearest face must not drop by more than a small tolerance (today: 444 → 36 of 19,800).

### F2 — Per-block, last-write mesh acknowledgment lets a torn mesh be recorded as current; the retry never fires in exactly the window Sodium drops requests
- **Severity:** Major (persistent wrong snow on some leaf blocks/ground columns of a section until an unrelated rebuild; Sodium and Iris only). **Confidence:** High (static, concrete interleaving below). **Status:** established by static analysis; not reproduced.
- **Location:** `SnowSystem.meshCoverage` `src/client/java/dev/frostedfoliage/client/world/SnowSystem.java:249-263` (ack written per block, line 258-259), `current()` `:294-298` (compares only the last write), `retryLostRebuilds` `:279-292`; `GroundSnowSystem.meshLayers` `GroundSnowSystem.java:79-91` (line 89) and `retryLostRebuilds` `:217-241` (line 232-233). Callers: `SnowModels.SnowModel.emitQuads` `SnowModels.java:126`, `emitGround` `:146`.
- **Renderer facts (verified):** Sodium `RenderSectionManager.scheduleRebuild`: `if (section != null && section.isBuilt()) { … upgradePendingUpdate … }` — requests are ignored until the first build result has been applied: `BuiltSectionInfo.flags` never contains `MASK_IS_BUILT`; `RenderRegion.setSectionRenderState` stores `info.flags | RenderSectionFlags.MASK_IS_BUILT` when `RenderSection.setInfo` applies a result, and `clearSectionRenderState` resets to `NONE`. `onSectionAdded` queues `INITIAL_BUILD` for non-air sections. `submitSectionTask` never cancels a running job; a section may have several jobs in flight, and `RenderSection.addMeshBuildOutput` keeps the output with the greatest `submitTime` (older results are ignored). One worker thread meshes one section per job, iterating y, z, x (`ChunkBuilderMeshingTask.execute`). Vanilla's `LevelExtractor.extract` only consumes dirty flags for visible sections that are compiled or have all neighbours, and `SectionUpdateTracker` keeps the flag otherwise; `SectionRenderDispatcher.createCompileTask` cancels the previous task. So vanilla never loses a request; the whole retry mechanism exists for Sodium's unbuilt window.
- **Interleaving (Sodium):**
  1. Chunk arrives → `onSectionAdded` queues `INITIAL_BUILD`; mod `load()` → `discover` → capture queued.
  2. Section becomes visible; worker W starts initial job J. For the first leaf block `b1`, `meshCoverage` reads snapshot `S1` (or `null` if not yet captured → coverage 0, no ack) and writes `meshed[K] = (S1, p, a)`.
  3. Client tick: the mod publishes `S2` (`snapshots.put`, line 223) and requests a rebuild → `setSectionDirty` → Sodium `scheduleRebuild` → `!isBuilt()` → **dropped**. (A progress step, `appearance++`, or ground `look++` behaves the same.)
  4. J continues; for a later leaf block `b2`, `meshCoverage` reads `S2` and writes `meshed[K] = (S2, p, a)` — last write wins.
  5. J's output is applied; `IS_BUILT` set. The mesh has `b1` from `S1`/null and `b2` from `S2`.
  6. `retryLostRebuilds`: `current(seen=(S2…), data=S2…)` → **true** → `retries.settled(K)`. No retry, ever. The torn section persists until something else rebuilds it (a block update within one section, a later progress step, a settings change, F3+A).
  The retry *does* recover when the publication lands after J's last eligible block (including the completion→apply gap), because then the ack is `S1 ≠ S2`. For a canopy-filled section the last foliage block is near the end of the job, so the unrecoverable part of the window is the larger part. At steady full snow (common in snowy biomes, and always with *Snowy biomes stay frosted*) newly streamed sections whose first capture lands mid-initial-build keep "bald" leaf blocks indefinitely in a static forest.
  The same hole exists for virtual ground snow (`meshLayers` acks per ground block) and for the cleanup direction (see F5).
- **What `LostRebuildTest` establishes:** that a rebuild request issued while `DropSectionRebuildsMixin` cancels `setSectionDirty(III)V` is re-requested later and a subsequent `SnowModel.emitQuads` observes full coverage (`SnowModelMeshMixin` records `system.coverage(pos)` at emission — correctly without touching production ack state). It records one value per section (last block), runs on the vanilla renderer by default, and **drops requests while no meshing job is in flight**, so it cannot observe a torn initial build and never exercises Sodium's real drop. "Model emission occurred" is the observation point; mesh acceptance/publication is not observed.
- **Smallest fix:** acknowledge the **first** observation of each worker-section run instead of the last. Keep a `ThreadLocal` run context in `SnowSystem` (and `GroundSnowSystem`): `{long key; long[] seen = new long[64]}`; in `meshCoverage(pos)`, compute `idx = (y&15)<<8|(z&15)<<4|(x&15)`; if `key != run.key || run.seen(idx)` (a position revisited ⇒ a new job), reset the run and write `meshed[key]` with the state observed *now*; otherwise do not write. A job that straddles a change then acks the older state, `current()` fails, and the retry fires (it keeps backing off until `IS_BUILT` makes the request land). Concurrent jobs on other workers write their own first observation; since every write reads the live state at write time, later writes are never older. ~25 lines, no new threads or locks.
- **Regression test:** factor the ack bookkeeping into a pure class (`MeshAcks.observe(workerRun, key, idx, state)` / `current(key, state)`) and unit-test the torn sequence above directly (JUnit, runs in CI). Then extend `LostRebuildTest`: a test mixin that blocks the worker thread on a latch at a chosen leaf position while the test turns preview on with `dropRebuilds=true`, releases the latch, clears `dropRebuilds`, and asserts `stale>0` within 20 ticks and that the per-block *minimum* recorded coverage in the section reaches 1.0 within 400 ticks. Run it with `-PtestRenderer=sodium`.

### F3 — Unchanged recaptures replace the snapshot object; identity-based freshness then forces a retry rebuild
- **Severity:** Major for the ground system during exploration (sustained unnecessary chunk-builder work), Moderate for foliage (bounded bursts). **Confidence:** High (static). **Status:** static; measurement protocol given.
- **Location:** `SnowSystem.java:221-226`: `changed = !data.sameEnvironment(old)`; `snapshots.put(key, data, …)` **unconditionally** (223); `scheduler.captured(key, …, changed)` deliberately requests no rebuild when unchanged (226) — but `meshed.get(key).snapshot() != data` is now true by identity (`:258`, `:297`), so the next `retryLostRebuilds` (every 20 ticks) marks the section stale and `RetryBackoff.due` schedules `scheduler.rebuild(key)` one period later (`core/RetryBackoff.java:20-27`). `GroundSnowSystem.java:191-194`: `changed = !next.same(old) && …`; `snapshots.put(key, next, limit())` unconditionally; `retryLostRebuilds` `:232-233` compares `seen.cover() == cover` by identity.
- **Triggers:** any recapture that the renderer has not *also* rebuilt in the same main-loop iteration. Immediate single-section recaptures caused by a block update are masked, because `Minecraft.runTick` runs `tick()` (packet → `setBlocksDirty` → mod `changed()` → END_CLIENT_TICK capture → new object) before `renderFrame` (extract → compile reads the new object), so the ack matches. Queued recaptures are not masked:
  - **Ground, every chunk load:** `GroundSnowSystem.load` → `invalidateAround(cx, cz, false)` (`:122`, `:151-158`) recaptures the 8 neighbours at 1–2 per tick. Unchanged covers are replaced; every neighbour section with virtual snow becomes "stale" and is rebuilt 20–40 ticks later. While moving through a snowy forest the capture queue is continuously fed (≈40 chunk loads/s at 20 m/s and 16 chunks → far more invalidations than the 20–40 captures/s budget), so **every retained ground chunk is recaptured on a rolling basis and each one costs 1–2 spurious section rebuilds**: an estimated 20–40 extra section rebuilds per second on the chunk builder, sustained while the player moves and nothing has changed. (The recaptures themselves are cheap, ≈0.065 ms each per the docs' measurement.)
  - **Foliage:** `configure` with `diff.exposure()` (e.g. *canopy delay* slider) or `tagsLoaded` → `recaptureAll` → every retained section is recaptured and, if unchanged, rebuilt anyway (4096 extra rebuilds at the default cache) — exactly the burst the "keep old snapshots usable" design (`SnowSystem.java:66-68`) was meant to avoid. Multi-section `changed()` invalidations (height changes, leaf-decay bursts across sections) and biome/chunk re-sends (`load()` on a retained chunk) add smaller bursts.
- **Why `BlockUpdateBenchmark` passes:** its "identical environment triggered a rebuild" check (`src/gametest/java/dev/frostedfoliage/test/BlockUpdateBenchmark.java:110-115`) exercises one immediate recapture, which the loop ordering above masks; `settled()` waits 40 ticks, long enough for the retry to show up, so the check would catch a *queued* case — but the fixture never queues one. `GroundSnowTest`'s quiet-terrain check (`GroundSnowTest.java:177-181`) idles; it never streams chunks.
- **Invariant violated:** "Recaptured snapshots are compared byte-for-byte, so an unchanged environment does not enqueue a remesh" (architecture.md, Cost controls). The scheduler honours it; the retry layer overrides it.
- **Smallest fix:** keep the old object when content is equal. `SnowSystem.tick`: `if (changed) snapshots.put(key, data, …);` (first capture has `old == null` ⇒ `changed == true`). `GroundSnowSystem.tick`: `if (old == null || !next.same(old)) snapshots.put(key, next, limit());` (content-equal covers keep their identity; `changed` keeps gating marks/rebuilds, and the `candidates` flag still updates because differing content is always stored). Three lines.
- **Regression test:** in package `dev.frostedfoliage.client.world` (as `GroundDiscoveryTest` already is): settle a world with virtual ground snow, read `groundRebuilds`, call `ground.load(neighbourChunk)` for an already-retained chunk (simulates a chunk re-send / biome packet without the renderer's own dirtying), wait 60 ticks, assert `groundRebuilds` unchanged. Same for foliage with `system.load(level, retainedChunk)` and `rebuilds`. Currently both would observe increments.

### F4 — Frosted falling-leaf particle sprites are generated without any size cap or budget
- **Severity:** Moderate (unbounded atlas/VRAM growth with HD particle packs; a particle-atlas stitch failure fails the whole reload and triggers Minecraft's vanilla-only rollback). **Confidence:** High (static). **Status:** static.
- **Location:** `src/client/java/dev/frostedfoliage/client/render/SnowParticleSource.java:42-49, 53-71`. Every texture referenced by a `particles/*leaves.json` definition is decoded and copied at full resolution (`NativeImage.read` → per-pixel `frostPixel` → new `SpriteContents`). `TextureBudget` (`core/TextureBudget.java`) and the 65,536-pixel source cap in `SnowSpriteSource.run` (`SnowSpriteSource.java:77`) cover block masks only.
- **Cost model:** vanilla has ~50 leaf particle sprites (`leaf_0..11`, cherry, pale oak, three poplars…). At 16× that is negligible. A 64× particle pack makes each copy 1024² = 1 M texels: ≈50 M texels (≈200 MiB RGBA before mipmaps) added to the particle atlas — more than six times the entire block-mask budget — with no warning. At 128× the vanilla copies alone already approach a 16384² atlas; the mod's copies push it over → `StitcherException` → reload failure where vanilla alone would have loaded.
- **Ownership:** correct — the image is closed on any exception (`finally`), and ownership transfers to `SpriteContents` on success (`image = null`).
- **Smallest fix:** apply the same 65,536-pixel source cap (skip + one warning), and count accepted particle texels against `TextureBudget.MAX_TEXELS` (or a separate small cap). ~6 lines.
- **Regression test:** extend `ResourceBudgetTest` with a scaled leaf particle texture (reuse `writeScaled`) and assert that the frosted copy is skipped above the cap and `SnowParticles` falls back to the vanilla sprite with the one-time warning.

### F5 — Cleanup rebuilds are not recoverable once the snapshot has left the retained set (Sodium unbuilt window)
- **Severity:** Moderate (stale white foliage / ground snow on an evicted, discarded or resized-out section until an unrelated rebuild; Sodium/Iris only, narrow window). **Confidence:** Medium (static; depends on an eviction coinciding with an in-flight initial build). **Status:** static.
- **Location:** `SectionScheduler.evict` `core/SectionScheduler.java:63-68` removes the snapshot immediately and queues the key in `retired`; `SnowSystem.tick` serves it once (`:229-235`); `retryLostRebuilds` treats keys without a snapshot as settled (`:285`) and deletes their `meshed`/`retries` entries (`:290-291`). Ground: `GroundSnowSystem.remove`/`mark` `:160-165` and `retryLostRebuilds` `:232` (`cover == null ⇒ current`), `:239-240`.
- **Interleaving:** the initial build J of a far section reads a snowy snapshot `S` for its early blocks; the scheduler evicts the key (closer section admitted, cache shrink, foliage excluded via `discard`); `removeSnapshot` nulls it; J's later blocks read `null` (no snow, no ack); the cleanup request issued from `retired` is dropped (`!isBuilt()`); J is applied with partial snow; `retryLostRebuilds` sees `data == null`, settles the key and drops the ack. Nothing will rebuild it except re-admission (which does queue a rebuild) or an unrelated event. For `discard` after an *Exclude blocks* edit this is user-visible: some excluded leaves stay white.
- **Smallest fix:** keep retrying keys whose last ack had snow until a mesh is observed without one: in `meshCoverage`, when `snapshot == null` and `meshed` holds a snowy ack, remove the entry (that *is* the "meshed without snow" ack); in `retryLostRebuilds`, for `meshed` entries whose snapshot is gone and whose recorded snapshot `hasSnow()`, keep them and issue `levelExtractor.setSectionDirty` through the same `RetryBackoff` instead of deleting them. Bounded by `meshed` (≤ retained + transient). ~12 lines; mirror in the ground system (`seen.cover().any()`).
- **Regression test:** `LostRebuildTest` variant: with full snow meshed and `dropRebuilds=true`, shrink `maxCachedSections` so the probe section is evicted (or exclude its leaves), wait 40 ticks, clear `dropRebuilds`, assert the per-block recorded coverage of the section returns to 0 within 400 ticks.

### F6 — `SectionScheduler.prioritize` re-sorts four ordered sets on every section-boundary crossing (measured 1.0 ms at the default cache, 4.6 ms at the maximum)
- **Severity:** Moderate at `maxCachedSections=16384` (visible hitch on the client thread when flying), Minor at the default 4096. **Confidence:** Confirmed by isolated measurement; in-game cost unmeasured. **Status:** reproduced in isolation.
- **Location:** `core/SectionScheduler.java:31-35` (`prioritize` rebuilds `retained`, `captures`, `rebuilds`, `retired` `TreeSet`s with a comparator that decodes `SectionPos` twice per comparison); called from `SnowSystem.updateFocus` `SnowSystem.java:161-168` whenever the player's section changes (every 16 blocks in any axis), and again from `GroundSnowSystem.updateFocus` `:170-173` for its own scheduler (≤ 4096 chunk keys).
- **Measurement:** `PrioritizeBench` (source in §6) fills the scheduler with realistic section keys, queues a rebuild for every key (what a stage change does) and times `prioritize` with the production-shaped distance lambda, JDK 25, 40 runs after warm-up: `retained=4096 pendingRebuilds=4096: best 0.74 ms, mean 0.99 ms`; `retained=16384 pendingRebuilds=16384: best 4.00 ms, mean 4.62 ms`. The ground scheduler adds up to another ~1 ms. These run on the client tick thread inside `tick()`/`load()`.
- **Smallest fix:** only `retained` needs an order (victim selection via `last()`); keep the work queues unordered and sort lazily on `poll` only when the comparator changed since the last poll (or pick nearest by a bounded scan of the small queues). Alternatively rate-limit reprioritisation (e.g. at most once per 10 ticks, or when the focus moved ≥ 2 sections). Either keeps behaviour: admission order unchanged, work order changes by at most one period.
- **Regression test:** JUnit: assert `prioritize` with 16,384 keys stays under a budget (e.g. 1 ms) — timing tests are flaky in CI, so prefer asserting the number of comparator invocations (inject a counting comparator) stays O(n) rather than O(n log n) per call, or assert the rate limit.

### F7 — `createGeometryKey` and `emitQuads` evaluate eligibility at different instants (latent TOCTOU)
- **Severity:** Minor (latent). **Confidence:** High that the race exists; **no current consumer** — neither Sodium 0.9.2 nor Fabric API 0.164.0 (renderer-api, indigo, model-loading) references `createGeometryKey` (bytecode grep of the pinned jars). **Status:** static.
- **Location:** `SnowModels.java:115-118` returns the wrapped model's cacheable key when `!system.active()` or the block is not foliage; `emitQuads` `:126` computes coverage independently. If `progress` or `config` flips between the two calls (microseconds apart, but both are `volatile` reads of state the client thread changes at any time), geometry with snow could be cached under a position-independent key and reused at other positions by a renderer that implements geometry caching.
- **Smallest fix:** return `null` from `createGeometryKey` whenever `system.foliage().test(state)` (foliage is always position-dependent while the mod is installed) and whenever a ground cover exists for the column, independent of `active()`.

### F8 — Chunk loads are discovered twice (Fabric `CHUNK_LOAD` event and the `onChunkLoaded` mixin)
- **Severity:** Minor (redundant work: two `discover` passes and two `ground.invalidateAround` calls per chunk packet; all idempotent). **Confidence:** High.
- **Evidence:** `FrostedFoliageClient.java:57` registers `ClientChunkEvents.CHUNK_LOAD` (fired by Fabric's `ClientChunkCacheMixin` at `TAIL` of `ClientChunkCache.replaceWithPacketData`), and `ClientLevelMixin.java:15-21` injects at `TAIL` of `ClientLevel.onChunkLoaded`, which `replaceWithPacketData` calls on every packet (`ClientChunkCache.java` line ~112) and `handleChunksBiomes` calls for biome updates. The mixin alone covers both cases.
- **Fix:** delete line 57 (keep the mixin, which the biome path needs). See §5.

### F9 — `stale` is not an error signal; tests that assert `stale=0` are environment-dependent
- **Severity:** Minor. **Confidence:** High.
- **Evidence:** `retryLostRebuilds` counts every retained snowy section whose ack is missing, including sections the renderer will never mesh (chunks the server sends beyond the client's render distance — `ClientChunkCache.calculateStorageRange` keeps `max(2, serverViewRange) + 3` chunks while the renderer uses `getEffectiveRenderDistance()` — and occluded/never-visible sections Sodium has not built). Those are retried forever at the 640-tick cap; each retry is a cheap no-op in both renderers (vanilla `SectionUpdateTracker.setDirty` on an out-of-range node is ignored; Sodium ignores unbuilt sections and `upgradePendingUpdate` returns early when nothing changes). `LostRebuildTest` waits for `" stale=0 "` and `" groundStale=0"`; in a world with any such section the wait times out although the behaviour under test is correct.
- **Fix:** report `stale` separately from "retrying" or exclude keys the renderer has no section for (not queryable through public API) — or simply document and make the test assert the probe section's own recovery, not a global zero.

### F10 — Configuration edge cases (all minor)
- `SnowConfig.clean` (`config/SnowConfig.java:40-44`) silently drops `null` entries, de-duplicates and truncates lists to 4096 without logging; an oversized `includeBlocks` list loses entries without any user-visible notice. Minor: log once when truncating.
- `ConfigStore.save` (`config/ConfigStore.java:50`) creates the temp file with `Files.createTempFile`, which uses owner-only permissions on POSIX; after the atomic move the config file ends up `0600`. Harmless for a single user; mention only.
- With **Mod Menu but no Cloth Config**, `ModMenuIntegration` returns a factory that yields `null` (`compat/ModMenuIntegration.java:9`); Mod Menu 21.0.0 treats any non-null factory as "has config screen" (`ModMenu.hasConfigScreen`), so the Configure button is enabled but inert (`ModsScreen.safelyOpenConfigScreen` guards `screen != null`). No crash; identical to Mod Menu's own default factory. Cosmetic.
- No defects found in parsing: wrong types, invalid identifiers, non-finite and extreme numbers, nulls and unknown fields are handled (§2.3).

## 3. Unverified risks (each needs a specific experiment)
1. **F1 under shader packs and during buildup.** Resolved for Complementary Reimagined r5.9.3: a `depth=true` run with the pack active passed, and its `depth-50-fast` capture shows the pack alpha-tests the solid pass (Fast leaves keep their holes), so the original defect was hidden there and the shipped Sodium + Fast rule now suppresses side snow that this pack would have drawn correctly — a documented trade-off, since the mod cannot tell packs apart. BSL is unchecked. No fixture captures Fast leaves during accumulation (case b).
2. **F2 frequency in the wild.** Add a test mixin recording per-block coverage and compute per-section min/max; fly through a large persistent-leaf forest at steady full snow with Sodium at render distance 16–32 for two minutes, idle 10 s, count sections with min < max. Expect a non-zero count; expect zero with the first-observation ack.
3. **F3 rate while streaming — measured.** `FlightTest` (1280 blocks at 10 m/s through natural snowy taiga, same seed and course, Sodium, shaders off): ground rebuild requests 1,414 (unfixed) → 1,217 (fixed), leaf rebuild requests 1,846 → 1,855. The audit's "20–40 extra rebuilds per second" estimate was too high: the renderer re-meshes neighbours on each chunk load, which refreshes most acknowledgments before a retry fires. Net effect of the fix in flight: about 14 % fewer ground rebuild requests.
4. **F6 in-game hitch.** Flight with the cache at 16,384; frame-time trace around section crossings.
5. **Sodium graph-dirtying by retries.** `upgradePendingUpdate` calls `markGraphDirty()` the first time a retry changes a built section's pending type; with thousands of stale sections after a stage change this may force extra occlusion-graph updates. Cost unmeasured.
6. **HD particle packs** (F4) — reload with a 64× particle pack and watch the particle atlas size / reload success.
7. **Multiplayer with a dedicated server** (documented as untested).

```java
import dev.frostedfoliage.core.SectionScheduler;
import java.util.Random;
public class PrioritizeBench {
    static long asLong(int x, int y, int z) { return ((long) x & 0x3FFFFF) << 42 | ((long) y & 0xFFFFF) | ((long) z & 0x3FFFFF) << 20; }
    static int sx(long k) { return (int) (k >> 42); } static int sy(long k) { return (int) (k << 44 >> 44); } static int sz(long k) { return (int) (k << 22 >> 42); }
    public static void main(String[] a) {
        for (int n : new int[]{4096, 16384}) {
            var s = new SectionScheduler(2 * 16384); var r = new Random(1); int side = (int) Math.ceil(Math.sqrt(n / 4.0)), c = 0;
            outer: for (int cx = -side / 2; cx <= side / 2; cx++) for (int cz = -side / 2; cz <= side / 2; cz++) for (int cy = 3; cy < 7; cy++) {
                if (c++ >= n) break outer; long k = asLong(cx, cy, cz); s.discover(k, n, false, x -> {}); s.captured(k, true, true); }
            for (long k : s.retainedKeys()) s.rebuild(k);
            long best = Long.MAX_VALUE, total = 0; int runs = 40;
            for (int i = 0; i < runs + 5; i++) { int px = r.nextInt(side) - side / 2, pz = r.nextInt(side) - side / 2; long t0 = System.nanoTime();
                s.prioritize(k -> { long dx = (long) sx(k) - px, dy = (long) sy(k) - 4, dz = (long) sz(k) - pz; return dx * dx + dy * dy + dz * dz; });
                long t = System.nanoTime() - t0; if (i >= 5) { total += t; best = Math.min(best, t); } }
            System.out.printf("retained=%d prioritize best=%.2f ms mean=%.2f ms%n", s.size(), best / 1e6, total / 1e6 / runs);
        }
    }
}
```
